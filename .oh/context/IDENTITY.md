# Identity

## Lessons learned (append-only)

- **2026-07-24**: Always run both review loops — adversarial critique of the spec before building, and adversarial audit of the real diff after. They catch structurally disjoint defect classes: spec critique finds design and coherence gaps that code review is too close to see, while a diff audit finds defects that exist only once the code exists and cannot be derived from any specification. Neither substitutes for the other, and skipping the second one is not a saving.
- **2026-07-27**: Never treat a green suite as evidence that a guard works. A guard fails silently in three distinct ways — it asserts a proxy instead of the behaviour, its pattern does not fire on the construct that matters, or a surrounding error handler rescues the failure it should have surfaced. All three read as coverage. Before relying on any load-bearing assertion, break the thing it protects and watch it go red; if it stays green, the guard is decoration.
- **2026-08-08**: Always verify that a placement flag actually took effect before launching work through it. A cwd/path flag that silently resolves against the wrong directory fails identically to success — the command returns clean, the response may even echo the path you asked for, and the work lands somewhere else. Confirm the resulting state, not the accepted argument.
- **2026-08-13**: Always resolve a convention question against the spec that states it, never against a sample of recent artifacts. A handful of neighbouring examples can be unanimous and still wrong — they may all be repeating the same mistake, made the same day, by peers reading the same incomplete summary you did. And when a deterministic checker disagrees with you, exhaust "I am wrong" before "the checker is broken": that ordering is the cheap one, because dismissing a correct check costs the defect plus the ticket filed against the thing that caught it.
- **2026-08-13**: A red is not automatically *your* red. Watching a guard go red proves it fired, not that it fired for your reason — so attribute the failure before trusting it: match the assertion's own message rather than a non-zero exit, and confirm the detection disappears when that one assertion is deleted. Two failure modes hide inside a plausible-looking red: a fixture that silently never applied, so the subject was never broken at all, and a guard that never ran because the harness aborted first — a probing `grep` under `set -o pipefail` exits non-zero with an *empty* message, which reads exactly like a catch.
