## Codebase Patterns

- Tests are vitest, run with `npx vitest run` (`pnpm test` fails — vitest is not in root `node_modules`; only `.oh/cli` deps are installed). Typecheck: `pnpm run typecheck`.
- Vitest include globs: `.oh/scripts/__tests__/**`, `.pi/**/__tests__/**`, `.oh/cli/**/__tests__/**`.
- `.oh/cli/src/__tests__/runtime-catalog.test.ts` holds a *synchronization* test: the microsandbox glibc remediation string must name the base image the Dockerfile actually pins. Changing `FROM` without the catalog string turns it red.
- Eval probes are standalone bash: `bash .oh/evals/probes/<name>.sh`, exit 0 PASS / 1 REGRESSION.
- CHANGELOG `[Unreleased]` bullets are capped at 250 chars by `changelog-entry-length.sh`.
- The repo strips explanatory comments from tracked code (#837), but deliberate, load-bearing comments (the Cloudflare 404 exception) are allowed and no probe forbids them.
- Confirmed live: `pkg.cloudflare.com/cloudflared/dists/trixie/Release` -> 404, `.../bookworm/Release` -> 200, `download.docker.com/linux/debian/dists/trixie/Release` -> 200.

## US-004 — 2026-08-26 21:22 UTC

**Title**: Validate arm64 and optional installers
**Files changed**: `.github/workflows/sandbox-compatibility.yml`, `.oh/evals/probes/sandbox-boot-guard-ci.sh`, `CHANGELOG.md`
**Commit**: 953f7dc4
**Result**: PASS

### What I did
Added a Dockerfile-path-scoped compatibility workflow with two jobs. The arm64 job prefers a native runner through `vars.CI_RUNNER_ARM64`, falls back to QEMU plus Buildx, builds `linux/arm64` with `load: true` so the Dockerfile's own `sha256sum -c -` and `herdr --version` checks execute, then runs the reusable verifier against the loaded image. The optional job builds one amd64 image with all four `INSTALL_*` args true, re-runs the verifier, and reports a version from `hermes`, `deepagents`, `opencode` and `grok`. Permissions are `contents: read`; there is no login, no push, no secret. Extended `sandbox-boot-guard-ci.sh` rather than adding a probe: it now also asserts the boot guard job name, the verifier invocation, and every compatibility contract, and fails if `release.yml` starts referencing the new workflow.

### Learnings for future iterations
The path filter is the load-bearing design choice. The boot guard's `.oh/**` filter would have fired these vendor installer builds on every harness edit, so the probe asserts the narrow Dockerfile filter *and* explicitly rejects a broad `.oh/**` entry in this workflow — the cheaper failure mode is worth guarding against directly. Confirmed both new probe branches fail correctly by deleting the workflow and by flipping the arm64 platform and one build arg in a scratch copy.

`oh-init-headless-config.sh` skips whenever `.oh/cli/dist/` is absent, which silently turns the 94/0/3 baseline into 93/0/4. Run `pnpm run build` before reading eval counts, or a clean run looks like a lost probe.

## US-003 follow-up — 2026-08-26 21:45 UTC

**Title**: Report the tool's own version line under emulation
**Files changed**: `.oh/scripts/verify-sandbox-image.sh`, `.oh/scripts/__tests__/verify-sandbox-image.test.ts`
**Result**: PASS

### What I did
CI evidence from the arm64 job showed every tool row printing `ok: gh --version -> WARNING: The requested image's platform ...` instead of a version. `docker run` emits that warning on stderr under QEMU and `2>&1` put it first, so `head -1` reported the runner's complaint rather than the tool. The verifier now skips that warning line and fails a tool that exits cleanly with no version line at all. Added a 14th test that arms the warning and asserts the real line survives.

### Learnings for future iterations
`head -1` of a merged `2>&1` stream reports whichever stream spoke first, which under emulation is never the one being measured. The check was passing while its evidence was worthless — a green check whose output does not name what it verified is not evidence. Real CI logs caught what every local unit test missed, because the fake `docker` never emitted the warning.
