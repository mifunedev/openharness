# progress

## Codebase Patterns

- **The task folder is tracked but gitignored.** `.oh/tasks/<slug>/` matches a `.gitignore` rule,
  yet `prd.md` / `prd.json` / `progress.txt` are already tracked (added with `-f` when scaffolded).
  A plain `git add .oh/tasks/...` fails with "paths are ignored" AND aborts the whole `git add`
  invocation — including the non-ignored paths listed alongside it. Stage the task folder with
  `git add -f` in a **separate** command from the rest of the story's files.
- **Quality-check script names.** From the repo root: `pnpm run typecheck` (no hyphen; delegates to
  `npm --prefix .oh/cli run typecheck` → `tsc --noEmit`) and `pnpm test` (vitest, 39 files / 481
  tests, ~5s). `pnpm run type-check` does not exist. Root `lint` is a no-op.
- **New RFCs must be indexed in TWO places.** `.oh/docs/rfcs/README.md` (the `## Index` table) and
  `.oh/docs/README.md` (the flat RFC bullet list, ~line 74-78). CHANGELOG #686 records the repo
  paying for a missed index entry, so treat both rows as part of "create an RFC", not scope creep.
- **Ground-truth the socket/dockerd facts before citing them.** Verified this iteration:
  `.devcontainer/docker-compose.yml:20-26` states the host socket is NOT mounted by default;
  `.oh/scripts/docker-compose.sh:136` appends `docker-compose.docker-sock.yml` only when
  `truthy()` (`:63`) accepts `sandbox.docker_socket` / `DOCKER_SOCKET`; `.devcontainer/Dockerfile:37`
  installs `docker-ce-cli` + `docker-compose-plugin` and no `dockerd`.
- **Writing any `.env` path trips the secret-exposure guard, and `rm -rf "$var"` trips the safety
  net.** Verifying the docker-sock overlay needs `DOCKER_SOCKET=true bash .oh/scripts/docker-compose.sh
  --repo-dir <dir> --print-argv config` (the script reads the env var before `.devcontainer/.env`,
  `docker-compose.sh:133`) — never write a `.env` fixture. Use literal `/tmp/<name>` paths, not
  `$(mktemp -d)` captured in a shell var, when a cleanup `rm -rf` follows. Heredoc-piped
  `git commit -F -` is also blocked; use repeated `-m` flags for multi-paragraph messages.
- **Scratch-verify new library code before committing, then delete the scratch.** A temporary
  `.oh/cli/src/__tests__/zz-<story>-scratch.test.ts` run with
  `npx --prefix .oh/cli vitest run <path>` exercises code whose real tests belong to a later story,
  without colliding with the file that story must create. Delete it and confirm with `git status`
  before staging.
- **The base compose bind is `..:${OH_PROJECT_ROOT:-/home/sandbox/harness}`** — a host path mapped
  to a fixed in-target path, so host and target paths are NOT identical in general. The RFC's
  "identical-path mapping only" stance is therefore a **contract-level** restriction (nothing above
  the seam translates paths; `resolveProjectRoot` yields one string used for both file reads and
  compose invocation), not a claim about the compose file. Do not restate it as a deployment fact.

### Learnings for future iterations

- **US-004's wiring is already determined by the adapter's failure semantics** (documented in the
  adapter's file header): a child that never ran throws `ExecutionSpawnError` whose message is
  byte-identical to today's `assertSpawned` text (`failed to run bash <script> (…)`,
  `failed to run docker exec <name>`); `attach()`/`exec()` return non-zero codes; `provision()`
  throws `ExecutionExitError` carrying the code, because `provision(): Promise<void>` has nowhere to
  return it. So `runSandbox` becomes
  `try { await target.provision(); return 0 } catch (e) { if (e instanceof ExecutionExitError) return e.exitCode; throw e }`
  — which reproduces `expect(await runSandbox(…)).toBe(17)` (lifecycle.test.ts:130) exactly. And
  `runShell` must catch `ExecutionSpawnError` with `code === "ENOENT"` and rethrow its own
  ``docker is required for `oh shell` but was not found on PATH`` (lifecycle.test.ts:436); any other
  `ExecutionSpawnError` propagates unchanged.
- **`resolveExecutionTarget()` returns `ResolvedExecutionTarget`** = `ExecutionTarget &
  Required<Pick<…,"provision"|"attach">>`, so US-004 calls `target.attach(…)` directly and gets
  `number`, not `number | undefined` — no `attach?.()` dance, and `runShell` keeps its `: number`
  signature.
- **The adapter never guesses a container name.** `container` is an option with no default; `attach`,
  `exec`, and `status` throw if it is unset. US-004 keeps the precedence chain (positional >
  `sandbox.name` > `DEFAULT_CONTAINER_NAME`) in `lifecycle.ts` — which is what the
  boundary-inversion criterion requires — and passes the resolved name to the factory. `runSandbox`
  passes no container (it needs none), so its one-call assertion (lifecycle.test.ts:114-120) holds.
- **`lifecycle.test.ts:114` asserts `calls` with `toEqual` on the whole array**, so `provision()` must
  stay exactly ONE child process. Do not let US-004 slip a `capabilities()` (a second, `--print-argv`
  child) into the `runSandbox` path.
- **Two micro-extensions beyond the literal AC text, both deliberate.** (1) The runner opts gained an
  optional `timeoutMs`, honored via `spawnSync`'s `timeout`, so `ExecRequest.timeoutMs` is real
  rather than silently ignored — same reasoning the PRD applies to `stderr`, and it mirrors
  `RemoteRunner`'s existing `opts.timeoutMs`. (2) `assertSpawned`/`requireLifecycleScript` moved into
  `runner.ts` alongside the runner instead of being copied, so the "missing lifecycle script …" and
  "failed to run …" strings exist in exactly one place. Both are additive; every existing fake runner
  still typechecks.
- **`capabilities()` advertises neither `"files"` nor `"ports"`** — the contract declares no method
  for either, so claiming them would be a capability no caller could use. If US-005 or a later slice
  wants them, add the method first.
